# Architecture

Both apps are organized **by feature**, not by file type. Everything about "invoices" lives in one place on each side, and the names match the PRD.

## Backend (`backend/`)

```
backend/
├── app/
│   ├── main.py              App factory: middleware, CORS, error handlers, routers
│   ├── core/                Infrastructure: config, security (JWT/hashing), exceptions, rate limit, logging
│   ├── db/                  Base class, session/engine, mixins, model registry for Alembic
│   ├── common/              Domain-agnostic helpers: pagination, money (Decimal), UTC time, base schemas
│   ├── api/
│   │   ├── deps.py          DB session, current user, role guards
│   │   └── v1/router.py     Mounts every module router under /api/v1
│   └── modules/             One package per business feature
│       ├── auth/  users/  categories/  products/  stock/
│       ├── invoices/        + numbering.py, pdf.py, templates/invoice.html
│       ├── exports/         + xlsx.py (workbook formatting)
│       ├── dashboard/       Aggregate SQL only
│       ├── ai/              + client.py (LLM adapter), tools.py (read-only tools), prompts.py
│       └── settings/        Business settings (tax rate, currency, ...)
├── alembic/versions/        Database migrations
├── scripts/seed.py          Admin user + sample data
└── tests/
    ├── unit/                Pure logic, no DB
    └── integration/         API + DB: permissions, stock rules, invoice transaction
```

### Module anatomy

| File            | Responsibility |
|-----------------|----------------|
| `router.py`     | HTTP only: parse input, enforce role, call the service, return schemas. |
| `schemas.py`    | Pydantic request/response models. |
| `service.py`    | Business rules and transaction boundaries. |
| `repository.py` | SQLAlchemy queries. No business logic. |
| `models.py`     | ORM tables and enums. |

**Dependency direction:** `router → service → repository → models`. Modules talk to each other only through **services**. For example, `invoices.service` calls `stock.service` to record SALE movements; it never touches the stock repository directly.

### Rules
- Money is `Decimal` / `NUMERIC`, never float.
- All timestamps are UTC.
- Stock quantity changes only through `stock.service`, inside a transaction.
- Errors are raised as `AppError` subclasses and rendered as `{ "detail", "code" }`.
- The AI module reads data only through `ai/tools.py` and never builds SQL.

## Frontend (`frontend/`)

React 19 + TypeScript, Vite, Tailwind CSS v4 with shadcn/ui (Radix), TanStack Query, React Router, React Hook Form + Zod, Recharts, Vitest + Testing Library.

```
frontend/src/
├── main.tsx             Entry: starts the mock API when enabled, renders <App>
├── app/                 Composition root: wires features together
│   ├── App.tsx, providers.tsx      Theme → Query → Auth → Tooltip/Toaster
│   ├── router.tsx                  Route table (PRD §9); pages are lazy-loaded
│   ├── route-guards.tsx            RequireAuth, RequireAdmin
│   ├── layout/                     App shell: sidebar, mobile drawer, top bar, search, user menu
│   └── pages/                      Not found, route error
├── components/
│   ├── ui/              shadcn/ui primitives (generated by the shadcn CLI, restyled to the design)
│   ├── common/          Design-system pieces: badges, StatCard, Panel, SegmentedControl, Pagination, DateRangePicker…
│   ├── feedback/        EmptyState, InlineAlert, ConfirmDialog, QueryError, AdminOnlyState
│   └── layout/          Page/PageHeader, AppLogo, ThemeToggle
├── features/            One folder per PRD area
│   └── <feature>/
│       ├── api/         <feature>.api.ts (HTTP calls) + queries.ts (TanStack Query hooks, cache keys)
│       ├── components/  Feature-specific components
│       ├── hooks/ utils/  Feature logic (e.g. invoices/utils/totals.ts)
│       ├── pages/       Route-level screens
│       ├── types.ts     Request/response types owned by the feature
│       └── index.ts     Public API for other features (hooks only)
├── mocks/               In-browser mock of the whole /api/v1 surface (MSW)
│   ├── data/seed.ts     Design's catalog + ~4 months of generated, consistent history
│   ├── db.ts            In-memory tables and the business rules (stock, invoices, analytics)
│   └── handlers/        One file per API resource
├── lib/                 api-client (JWT + refresh), query-client, money (cents), format, dates, theme
├── hooks/               Generic hooks
├── config/              env.ts, constants.ts
├── types/               API envelopes (api.ts) and shared entities (models.ts)
├── styles/              globals.css (design tokens → Tailwind/shadcn), print.css
└── test/                Test setup + app smoke test
```

Features: `auth`, `dashboard`, `products`, `categories`, `stock`, `invoices`, `assistant`, `users`, `settings`.

### Rules
- **Dependency direction:** `app → features → components / lib / types`. `components/` never imports from `features/`.
- **Cross-feature use goes through `index.ts` only** (e.g. invoices uses `useProducts` from `@/features/products`). Pages are never exported there; the router imports them directly so each screen is its own chunk.
- **API types are snake_case**, exactly as the backend sends them; no mapping layer.
- **Money** arrives as decimal strings; arithmetic happens in integer cents via `lib/money.ts`.
- **Design tokens** live only in `styles/globals.css` (light + dark). Components use token classes (`bg-subtle`, `text-warning`, `bg-primary-soft`…), never raw colours. The printed invoice is the one exception: fixed black on white.
- **Role checks in the UI are hints;** the backend enforces them (AUTH-4).

### Mock API
Until the backend exists, `VITE_USE_MOCKS=true` (the default) serves every `/api/v1` endpoint from the browser via Mock Service Worker. The mock applies the PRD rules (no negative stock, atomic invoices, cancel → reverse movements, role checks, AI rate limit) so the UI is built against realistic behaviour. Data resets on reload. Set `VITE_USE_MOCKS=false` to talk to the real backend; no feature code changes.

Endpoints the UI needs beyond the PRD §8 table (to be implemented in the backend): `GET /auth/me`, `GET /invoices/summary`, `GET /invoices/next-number`, `GET /ai/quota`.

## Decisions

Answers to the PRD's open questions (§12) and other choices made along the way.

| Topic | Decision |
|-------|----------|
| UI component library | shadcn/ui on Tailwind CSS. Components live in `src/components/ui/`, with the `@/` alias pointing to `src/`. |
| Language / direction | English only (LTR) for v1. Arabic/RTL is deferred. |
| Default tax rate | `0` (configurable via `DEFAULT_TAX_RATE` and the settings table). |
| Currency | SAR (configurable via `DEFAULT_CURRENCY` and the settings table). |
| LLM provider | Not decided yet. |
| Customer management | Not decided yet. |
