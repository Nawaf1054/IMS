# Architecture

Both apps are organized **by feature**, not by file type. Everything about "invoices" lives in one place on each side, and the names match the PRD.

## Backend (`backend/`)

```
backend/
├── app/
│   ├── main.py              App factory: middleware, CORS, error handlers, routers
│   ├── core/                Infrastructure: config, security (JWT/hashing), exceptions, rate limit, logging
│   ├── db/                  Base class, session/engine, mixins, model registry for Alembic
│   ├── common/              Domain-agnostic helpers: pagination, money (Decimal), UTC time, base schemas
│   ├── api/
│   │   ├── deps.py          DB session, current user, role guards
│   │   └── v1/router.py     Mounts every module router under /api/v1
│   └── modules/             One package per business feature
│       ├── auth/  users/  categories/  products/  stock/
│       ├── invoices/        + numbering.py, pdf.py, templates/invoice.html
│       ├── exports/         + xlsx.py (workbook formatting)
│       ├── dashboard/       Aggregate SQL only
│       ├── ai/              + client.py (LLM adapter), tools.py (read-only tools), prompts.py, formatting.py
│       └── settings/        Business settings (tax rate, currency, ...)
├── alembic/versions/        Database migrations
├── scripts/seed.py          Admin user + sample data
└── tests/
    ├── unit/                Pure logic, no DB
    └── integration/         API + DB: permissions, stock rules, invoice transaction
```

### Module anatomy

| File            | Responsibility |
|-----------------|----------------|
| `router.py`     | HTTP only: parse input, enforce role, call the service, return schemas. |
| `schemas.py`    | Pydantic request/response models. |
| `service.py`    | Business rules and transaction boundaries. |
| `repository.py` | SQLAlchemy queries. No business logic. |
| `models.py`     | ORM tables and enums. |

**Dependency direction:** `router → service → repository → models`. Modules talk to each other only through **services**. For example, `invoices.service` calls `stock.service` to record SALE movements; it never touches the stock repository directly.

### Rules
- Money is `Decimal` / `NUMERIC`, never float.
- All timestamps are UTC.
- Stock quantity changes only through `stock.service`, inside a transaction.
- Errors are raised as `AppError` subclasses and rendered as `{ "detail", "code" }`.
- The AI module reads business data only through `ai/tools.py` (which calls the dashboard and products services) and never builds SQL for it. `ai/repository.py` only touches its own `ai_requests` table (the rate limit).
- Only `ai/client.py` imports the LLM provider's SDK.

## Frontend (`frontend/`)

React 19 + TypeScript, Vite, Tailwind CSS v4 with shadcn/ui (Radix), TanStack Query, React Router, React Hook Form + Zod, Recharts, Vitest + Testing Library.

```
frontend/src/
├── main.tsx             Entry: loads global styles, renders <App>
├── app/                 Composition root: wires features together
│   ├── App.tsx, providers.tsx      Theme → Query → Auth → Tooltip/Toaster
│   ├── router.tsx                  Route table (PRD §9); pages are lazy-loaded
│   ├── route-guards.tsx            RequireAuth, RequireAdmin
│   ├── layout/                     App shell: sidebar, mobile drawer, top bar, search, user menu
│   └── pages/                      Not found, route error
├── components/
│   ├── ui/              shadcn/ui primitives (generated by the shadcn CLI, restyled to the design)
│   ├── common/          Design-system pieces: badges, StatCard, Panel, SegmentedControl, Pagination, DateRangePicker…
│   ├── feedback/        EmptyState, InlineAlert, ConfirmDialog, QueryError, AdminOnlyState
│   └── layout/          Page/PageHeader, AppLogo, ThemeToggle
├── features/            One folder per PRD area
│   └── <feature>/
│       ├── api/         <feature>.api.ts (HTTP calls) + queries.ts (TanStack Query hooks, cache keys)
│       ├── components/  Feature-specific components
│       ├── hooks/ utils/  Feature logic (e.g. invoices/utils/totals.ts)
│       ├── pages/       Route-level screens
│       ├── types.ts     Request/response types owned by the feature
│       └── index.ts     Public API for other features (hooks only)
├── lib/                 api-client (JWT + refresh), query-client, money (cents), format, dates, theme
├── hooks/               Generic hooks
├── config/              env.ts, constants.ts
├── types/               API envelopes (api.ts) and shared entities (models.ts)
├── styles/              globals.css (design tokens → Tailwind/shadcn), print.css
└── test/                Test setup (jsdom stubs)
```

Features: `auth`, `dashboard`, `products`, `categories`, `stock`, `invoices`, `assistant`, `users`, `settings`.

### Rules
- **Dependency direction:** `app → features → components / lib / types`. `components/` never imports from `features/`.
- **Cross-feature use goes through `index.ts` only** (e.g. invoices uses `useProducts` from `@/features/products`). Pages are never exported there; the router imports them directly so each screen is its own chunk.
- **API types are snake_case**, exactly as the backend sends them; no mapping layer.
- **Money** arrives as decimal strings; arithmetic happens in integer cents via `lib/money.ts`.
- **Design tokens** live only in `styles/globals.css` (light + dark). Components use token classes (`bg-subtle`, `text-warning`, `bg-primary-soft`…), never raw colours. The printed invoice is the one exception: fixed black on white.
- **Role checks in the UI are hints;** the backend enforces them (AUTH-4).

### API contract
The frontend always talks to the real backend; there is no mock mode. Each feature's `types.ts` is the contract: the backend's Pydantic schemas match those field names and shapes exactly.

The UI was first built against an in-browser mock API (MSW), removed after M7. `features/assistant/types.ts` defines the AI payloads; the backend's `ai/schemas.py` matches it.

Endpoints the UI needs beyond the PRD §8 table: `GET /auth/me`, `GET /invoices/summary`, `GET /invoices/next-number`, `GET /ai/quota`.

### Feature flags
`AI_ASSISTANT_ENABLED` in `config/constants.ts` is `true` since M8. Setting it to `false` hides the assistant again: `/assistant` then shows a blurred, non-interactive preview under a "Coming soon" card (`components/feedback/ComingSoon.tsx`), the product form's AI description button is disabled, and nothing calls `/ai/*`.

## Authentication (Supabase Auth)

```
Browser ── signInWithPassword / refresh ──► Supabase Auth
   │  Authorization: Bearer <Supabase access token>
   ▼
FastAPI ── verify JWT (JWKS or HS256 secret) ──► profiles row (role, is_active) ──► Postgres
```

- **Frontend:** `lib/auth-session/` wraps Supabase Auth (`supabase-session.ts`, supabase-js). `api-client.ts` asks it for the token and retries once after a refresh on 401. Supabase errors are mapped to the existing codes (`INVALID_CREDENTIALS`, `ACCOUNT_INACTIVE`).
- **Backend:** `core/security.py` verifies the token (audience `authenticated`, issuer `<SUPABASE_URL>/auth/v1`). `api/deps.py` loads the `profiles` row by `auth_user_id = sub` and rejects missing or inactive profiles (401). `require_admin` returns 403.
- **Users** (`profiles`): an integer `id` (used by the API and later FKs), `auth_user_id` (Supabase user), name, lower-cased email, role and active flag. There's no FK to `auth.users` because that schema only exists on Supabase. Role and active flag live here, not in Supabase metadata, so changes apply on the next request.
- **Admin actions** go through `modules/auth/supabase_admin.py` (secret key, server only). Create: Supabase user, then profile; if the profile insert fails, the Supabase user is deleted. Deactivate: `is_active=false` plus a Supabase ban, which stops token refresh. Self sign-up is off (`supabase/config.toml`).
- **Schema:** Alembic owns it; Supabase migrations are off. Every app table enables row-level security with no policies, so Supabase's public Data API can't read it. The backend connects as the table owner and isn't affected.
- **Tests and CI** use plain Postgres and sign HS256 tokens with a test secret. Supabase isn't needed.

## Decisions

Answers to the PRD's open questions (§12) and other choices made along the way.

| Topic | Decision |
|-------|----------|
| UI component library | shadcn/ui on Tailwind CSS. Components live in `src/components/ui/`, with the `@/` alias pointing to `src/`. |
| Language / direction | English only (LTR) for v1. Arabic/RTL is deferred. |
| Default tax rate | `0` (configurable via `DEFAULT_TAX_RATE` and the settings table). |
| Currency | SAR (configurable via `DEFAULT_CURRENCY` and the settings table). |
| Database & auth | Supabase: hosted Postgres + Supabase Auth. Local dev uses the Supabase CLI stack (`npx supabase start`); CI uses plain Postgres. |
| Python tooling | uv (`backend/pyproject.toml`, `uv.lock`); ruff for lint and format (instead of black). |
| Production DB connection | Supabase session pooler (port 5432, IPv4). If the transaction pooler (6543) is ever used, set psycopg `prepare_threshold=None`. |
| LLM provider | Google Gemini via the official `google-genai` SDK (Interactions API, stateless with `store=False`: the backend sends the conversation each time and Google keeps nothing). Only `ai/client.py` imports the SDK; the rest of the module uses provider-neutral message, tool-call and tool-result types, so swapping providers means one new adapter class. Default model `gemini-3.5-flash-lite` (`LLM_MODEL` overrides). Requests time out after `LLM_TIMEOUT_SECONDS` (30) with one retry. Every provider failure (no key, timeout, network, 4xx/5xx, a blocked or empty reply) becomes `503 AI_UNAVAILABLE`; details are logged with the key masked, never sent to the client. The key is read from server settings only (AI-6), and an empty key fails at request time, not at startup (AI-7). |
| AI tools | Five read-only tools in `ai/tools.py` (AI-2): sales summary, top products, low-stock products, category revenue, product search. Each has a hand-written JSON schema, a Pydantic model that validates the model's arguments (dates, `limit` ≤ 20, the dashboard's five-year cap) and a runner that calls the dashboard or products service. A runner returns data for the model plus a label (the "Data used" chip) and display rows, so the answer's rows and sources come from tool results, never from the model's text. Bad calls (unknown tool, invalid arguments) go back to the model as error results. The chat loop allows 5 model calls per question and 8 tool calls per round; the model is told to quote tool figures and never calculate its own. Insights (AI-4): the backend computes every figure and sends only those to the model, which returns JSON sections that are validated. |
| AI access | Every signed-in user may use the AI endpoints, as PRD §8 says ("All"). PRD §4 lists the assistant only under Admin; §8 was followed. |
| AI rate limit | `ai_requests` table (user, kind, time; index on `(user_id, created_at)`), rolling one-hour window of `AI_RATE_LIMIT_PER_HOUR` (20). The rules are in `core/rate_limit.py`, storage in `ai/repository.py`. The quota is checked before calling the model and a request is recorded only after it succeeded, so failures are free; `resets_at` is when the oldest counted request expires. Over the limit: `429 RATE_LIMITED`. Two simultaneous requests can both pass when one is left; for an hourly allowance that's acceptable. Rows older than the window are pruned when a new one is recorded. |
| Customer management | Not decided yet. |
| Category nesting | One level (CAT-2). A category that has subcategories can't be moved under another one (`NESTING_TOO_DEEP`). |
| Demo stock | Products are created at quantity 0; `seed --demo` then records one "Opening stock" IN movement per product (`demo_data.OPENING_STOCK`), so quantities match the design and PRD-4 holds. |
| Stock concurrency | `stock.service.apply()` is the only code that changes `Product.quantity`. Callers lock the product row first (`products_service.get_for_update`, `SELECT … FOR UPDATE`), so concurrent movements queue instead of overselling. Movements are stamped with `clock_timestamp()`, so time order matches balance order. A `CHECK (quantity >= 0)` backs it up. |
| Movement quantities | `stock_movements.quantity` is the signed change and `balance_after` the resulting quantity. For ADJUSTMENT the API takes the counted quantity and stores the difference. |
| Date filters | `start_date` / `end_date` are inclusive days in `BUSINESS_TIMEZONE` (default `Asia/Riyadh`). They become UTC bounds before querying, so the `created_at` indexes still apply. |
| Deleting products | A product that was never invoiced is hard-deleted along with its movement history (`ON DELETE CASCADE`). Invoiced products are only deactivated (PRD-2); `invoice_items.product_id` is `RESTRICT`, so the database enforces it too. |
| Invoice transaction | `invoices.service.create_invoice` checks the whole request first, then locks every product on it (`products_service.get_many_for_update`, in id order so concurrent sales can't deadlock), writes the invoice and its items, and calls `stock.service.apply()` for each SALE movement, with one commit (INV-4). Cancelling locks the invoice row, adds a reversal IN movement per line (`Reversal: <number> cancelled`, linked to the invoice) and sets `CANCELLED` (INV-6). |
| Invoice numbers | `INV-<year>-<5 digits>`, sequential per business-local year (INV-3). An `invoice_sequences` row per year is incremented with `INSERT … ON CONFLICT DO UPDATE` inside the invoice transaction: numbers are unique even under concurrent sales, and a failed invoice rolls its number back, so there are no gaps. `GET /invoices/next-number` only previews it. |
| Invoice totals | Stored on the invoice, never recomputed. Discount comes off the subtotal before tax, tax is rounded half-up to the cent, and the tax rate is copied from the settings (to 0.01%) when the invoice is created. CHECK constraints keep `total = subtotal − discount + tax_amount` and `line_total = quantity × unit_price`. Staff sell at the product price; only admins may send a different `unit_price`. |
| Invoice PDF | `invoices/templates/invoice.html` (Jinja2, autoescaped) mirrors the frontend's printable invoice and is rendered by WeasyPrint. WeasyPrint is imported only on a PDF request, so the API runs without its system libraries and answers `503 PDF_UNAVAILABLE`. The Docker image and CI install `libpango` and a font. |
| Token issuer | `SUPABASE_JWT_ISSUER` overrides the expected `iss` when the backend reaches Supabase at a different address than the one in tokens (docker-compose: `host.docker.internal` vs `127.0.0.1`). |
| Business settings | `settings` key/value table over defaults from the environment (`DEFAULT_CURRENCY`, `DEFAULT_TAX_RATE`, business name "My Business"). |
| Excel exports | `exports/xlsx.py` writes one sheet per export with openpyxl in write-only (streaming) mode: bold frozen header, autofilter, currency/date/integer formats, columns sized to their widest value (8–60 characters). Each module's repository has an `export_rows` query that selects plain columns (no ORM objects) with the same filters and order as its list, so the file matches the screen (EXP-5). Timestamps are written in business-local time. Text cells are forced to plain text, so a name starting with `=` can't become an Excel formula. More rows than one sheet holds (1,048,575) answers `422 EXPORT_TOO_LARGE`. |
| Dashboard figures | Summed by PostgreSQL in `dashboard/repository.py`; only `COMPLETED` invoices count. Revenue on the KPI cards and the sales chart is the invoice total (after discount, with tax); top products and category revenue use line totals (before discount and tax), since a discount isn't split across lines. Days are business-local: daily buckets group by `timezone(BUSINESS_TIMEZONE, created_at)::date`. Weekly buckets are 7-day blocks counted from the range start; monthly buckets follow the calendar. Subcategory sales roll up into their parent. Low and out-of-stock counts include active products only. Chart ranges are capped at five years. |
